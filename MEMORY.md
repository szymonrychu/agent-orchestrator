# agent-orchestrator memory

Lessons that outlive a session. Newest first.

- 2026-10-25, bench record (Q12), live release chart 0.1.0-main.a5b5a75, wrapper 0.2.0, `orch bench examples/bench.yaml` via port-forward, model claude-sonnet-5-5, fizzbuzz x3 repeats per arm. Per arm (p50 wall s / mean wall s, failed turns, mean tokens per run, verify pass, final leader epoch): single 6.1 / 5.3, 0, 194, 100%, none; rr3 4.6 / 4.3, 0, 185, 100%, 1; rr3-peers 4.7 / 4.6, 0, 213, 100%, 1; hive3 4.5 / 4.0, 0, 171, 100%, 1. Token multiple vs single: rr3 0.95x, rr3-peers 1.10x, hive3 0.88x. Verdict on "3 agents faster than 1": directionally yes (p50 about 25% lower, mean 13-25% lower for every 3-replica arm), but not established: the task finishes in about 5 s, so wall time is dominated by dispatch overhead, n=3 per arm, the 120 s chaos restart never fired, and the 3-replica arms did not differ from each other beyond noise. Tokens did not rise with replicas. No switch follows either way (Q12). Caveat: the shipped `examples/bench.yaml` says `model: sonnet`, which the live API rejects (422, allowed: claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5, claude-fable-5-1); the run used a copy with `claude-sonnet-5-5`.

- 2026-10-24, hive docs: amends the 2026-10-23 spec-immutability entry (D4): `spec.replicas` and `spec.init_scripts` are the only spec fields that change in place, with no generation bump and no pod roll; every other field stays fixed and `PATCH /api/v1/clusters/{id}` stays 405. Why: scaling and init scripts must work on a running hive without rolling agents that hold sessions and locks. Owned contract part `orch-spec-runtime-mutable`, documented in README `## API` Versioning.
- 2026-10-24, agent-to-orchestrator path (D1): agents call `/agent/v1` on a second listening socket of `orch api` (the agent port, `ORCH_AGENT_PORT`, 8001) that serves only `/agent/v1/*`, behind `HMAC(master_key, "agent:<cluster_id>")` mounted from the cluster Secret, plus caller-IP binding to `agents.pod_ip`; the matching agents row is the caller's identity. Why: the api has no auth of its own, so the agent surface gets its own port and token, and agents need synchronous answers. Rejected: per-agent tokens (one Secret per StatefulSet), wrapper events and the ingester (async, no answers), a separate agent-api process (a second writer), the same port with an exempt prefix (rides the ingress). The main port answers 404 for `/agent/v1`.
- 2026-10-24, tool visibility is fixed at render from `max_replicas` and `static`, not from the live replica count. Why: the pod spec must not depend on how many agents run now, or a scale would roll pods to change their tools; a hive is by definition a cluster whose cap exceeds 1. The renderer in `k8s/on_start.py` also owns the plugin name `orchestrator`: its entry replaces a user entry of that name, and specs naming it are rejected.
- 2026-10-24, wrapper peer seeds are rendered from the cap (`range(max_replicas or replicas)`), not the current replicas. Why: agents added by scaling then find each other without any pod rolling; a seed whose pod does not exist yet is simply unreachable until it starts.
- 2026-10-24, amends the 2026-10-23 layering entry: `api/agent.py` may now import `agent_orchestrator.tokens`, alongside `api/workspace.py`; the pin in `tests/test_api_clusters.py::test_api_never_imports_k8s_or_wrapper` (`token_users`) was widened from workspace.py alone to workspace.py and agent.py. Why: the agent route must verify the same derived token the renderer put in the pod env. No other api module may import `tokens`, `wrapper`, k8s or reconciler; only workspace.py may import `wrapper`.
- 2026-10-24, the feed and `hive_state` pushes run in the dispatcher (`dispatcher/hive.py`), not the ingester. Why: the dispatcher already owns `cluster_leaders` and the claim lock, and the ingester must stay a pure event writer with one subscription per agent; the leader row, the feed cursor and the per-agent hashes then have a single writer.
- 2026-10-24, `LEADER_GRACE_SECONDS` (30, `db/leadership.py`) and `PUSH_INTERVAL_SECONDS` (10, `dispatcher/hive.py`) are module constants, not settings. Why: they are protocol timings that tests and the docs pin, and an operator tuning them per deployment would only create untested combinations.

- 2026-10-25, hive push loop (`dispatcher/hive.py`): `cluster_leaders.state_hash` is a JSON map `{agent_id: hash}` (text column, dispatcher the only writer) so one unreachable agent never re-pushes the others; the lock is held only around the DB read and the DB write, never across wrapper HTTP. The feed settle window judges `events.created_at` (DB insert time, `DEFAULT clock_timestamp()` added to migration 0003, filled by the DB so the ingester stays the only writer), not `events.ts`: ts is the wrapper's envelope time, so a replayed catch-up row with an old ts and a low id committing late would count as settled and be skipped for good. Chosen over a pg_snapshot xmin test because one long transaction anywhere in the database would stall the feed. The push claims its work (feed cursor and per-agent hashes) in the locked read phase and undoes only failed hive_state claims afterwards, so a second dispatcher never repeats a push. Pending Bash calls and the in-memory read watermark are lost on a dispatcher restart: the stored cursor is held below the oldest pending call, so a restart can repeat a few feed lines, never skip one.

- 2026-10-23, exception to the additive-only `/api/v1` rule: `PATCH /api/v1/clusters/{id}` is removed (405, pinned by `tests/test_api_clusters.py::test_patch_cluster_retired_405`) and `POST /api/v1/clusters` needs exactly one of `spec` and `preset_id`. Why: a live spec edit bumped `generation` and rolled every agent pod of a running cluster; clusters now snapshot their preset spec at create and never change. Changing a spec means discarding the cluster and scheduling again from a preset. `check_spec` keeps its `stored` parameter only for the preset PUT (a stored out-of-list model, effort or image stays accepted when unchanged). The exception is documented in README `## API` Versioning.
- 2026-10-23, amends D5: the api now calls wrapper pods with derived per-cluster tokens, only through `api/workspace.py`, for the file and terminal proxies (user decision N1). Why: the wrapper is the only process with the workdir mounted and a PTY, and Kubernetes `pods/exec` is excluded, so there is no other way to serve a file tree or a terminal. Events stay stored, not proxied. Layering is pinned by `tests/test_api_clusters.py::test_api_never_imports_k8s_or_wrapper`: no other api module may import `agent_orchestrator.wrapper` or `agent_orchestrator.tokens`, and none may import k8s or reconciler. The derived token is sent only as the Authorization header (`WrapperTarget.token` is `repr=False`), and terminal ids are checked against `^term_[0-9a-f]{12}$` before any upstream path is built.
- Single-writer reading of "no shared state" (D2): the tatara rule "services talk only through the queue or HTTP APIs, no shared state" conflicts with a Postgres-only queue, so it means one writer per table. Queue tables (messages, commands, checks) are the only multi-writer tables, changed only through `WHERE status = '<expected>'` UPDATEs. Table writers are in README.md `## Architecture`.
- One session per pod: a pod is exactly one claude-code-wrapper session, and a single pod is a cluster of 1. Peer messaging, round-robin and context gauges are per pod, never per multi-session pod.
- Events are stored, not proxied (D5): the ingester keeps one SSE subscription per agent and stores every event (at-least-once delivery, exactly-once storage via UNIQUE(agent_id, session_id, seq)). Browsers and API clients read the stored rows, so history survives wrapper restarts, resume works from a global event id, and the api never holds wrapper tokens.
- openapi.json is generated: after any route or schema change run `uv run python -m agent_orchestrator.api.openapi > openapi.json`; tests/test_readme_api.py fails on drift and on undocumented routes.
- 2026-10-24: chart `components.<name>.podAnnotations` merge over global `podAnnotations` (component wins). Why: the cluster's oauth2-proxy admission webhook (Go injector 0.4.7) rejects any annotated pod whose first container has no ports, and global podAnnotations reach the port-less dispatcher/ingester/reconciler too, so SSO annotations must target the api pod alone.
- 2026-10-24: react-resizable-panels `Separator` pitfall: the library writes an INLINE `flex-basis: auto` (plus `flex-grow: 0; flex-shrink: 0`) on the separator element, which beats a styled `flex: 0 0 4px` shorthand, so a childless separator renders 0px wide and its colour never shows (dragging still works through pointer hit regions). Size it with an inline `style={{ flexBasis: ... }}` (props.style is spread after the defaults), never with a stylesheet `flex` rule. Why recorded: the dividers were invisible in the live UI while every jsdom test passed.
- 2026-10-24, amends D25 (prior web-ui epic: "event-driven refresh plus a manual refresh button; no inotify", user decisions U2, X2): the "Refresh files" button is removed. `FilesPanel` now polls `pollExpanded()` every 3 s while `document.visibilityState` is visible, plus one pass on `visibilitychange` to visible and on every event stream open, and refetches the open preview when its entry mtime or size changes in the parent listing. The stream path (`fileEvents`) stays for instant agent writes. Why: terminal shells, check jobs and any writer outside the agent hooks produce no events, and a tree that loaded in error (409) or missing only recovered by clicking. Still no inotify and no backend or API change: the tree reads the existing files API. No timer runs while the tab is hidden or the panel is unmounted.
