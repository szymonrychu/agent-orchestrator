# agents-orchestrator memory

Lessons that outlive a session. Newest first.

- 2026-10-25, rename (orchestrator-rename-sessions D1, D10): the repo, Python package, chart, image, OCI chart, managed-by label, Secrets and Services are named agents-orchestrator (package `agents_orchestrator`); the CLI `orch`, the `ORCH_` prefix, `X-Orch-*` headers and the `agent-<slug>` object prefix stay. No alias, shim or redirect in code. Why: the repo is one of the agents-* services, and the old name read as a single agent.
- 2026-10-25, the orchestrator's unit is a session (D2): routes `/api/v1/sessions`, schemas `Session*`, fields `session_id`, tables `sessions` and `session_leaders` (migration 0005), label `agents.szymonrichert.pl/session`, agent API `X-Orch-Session` and `ORCH_SESSION_ID`, with no alias (old routes 404). Kubernetes, CNPG and kind clusters keep their word (D12), and `tests/test_nomenclature.py` and `tests/test_project_name.py` guard every tracked file outside dated history (MEMORY.md, ROADMAP.md, CHANGELOG.md, docs/plans/). Why: one word for one thing across the API, the UI and the database.
- 2026-10-25, the wrapper's session id is `wrapper_session_id` (D3): `agents.wrapper_session_id`, `agents.wrapper_session_created_at`, `events.wrapper_session_id` (migration 0004) and EventView.wrapper_session_id; the `wrapper/` client keeps the wrapper's own `/v1/sessions`. Why: once the unit is a session, `session_id` is the foreign key to `sessions` and the wrapper's id would collide with it.
- 2026-10-25, amends D1 and D12: the UI moved to agents-web (imported from agent-orchestrator b7906aa355a91fa51ddd5e6e2d62df63c23f6744) and the api is API-only: no `frontend/`, no node stage in the image, no npm in CI. Why: services talk only through HTTP, and other services need UI entries without living in the orchestrator. After an orchestrator route change, regenerate `openapi.json`, then run `npm run sync:api -- orchestrator` in agents-web.
- 2026-10-25, scale-down drain (cluster-scaling D3): agents above `spec.replicas` drain instead of being cut; the StatefulSet keeps `max(target, 1 + highest busy draining ordinal)` replicas (busy: `agent_status.state` busy or a `dispatching`/`verifying` message), capped at the replicas already applied so a gone pod is never recreated, and gets the target after `ORCH_SCALE_DRAIN_SECONDS` (900) counted from `status.drain.since`. Why: a pod removed mid-turn loses the turn; the bound keeps a stuck turn from pinning capacity forever, and the interrupted turn then takes the existing verify path. `since` lives in `clusters.status` so a reconciler failover keeps the deadline. Only `spec.replicas` is overridden at render (`dataclasses.replace` + `spec.model_copy`), so the ConfigMap hash and pod template stay identical and no pod rolls. Rejected: refusing a scale-down while a victim is busy (stalls the leader's tool call) and cutting the turn (loses work).
- 2026-10-25, bench record (Q12), live release chart 0.1.0-main.a5b5a75, wrapper 0.2.0, `orch bench examples/bench.yaml` via port-forward, model claude-sonnet-5-5, fizzbuzz x3 repeats per arm. Per arm (p50 wall s / mean wall s, failed turns, mean tokens per run, verify pass, final leader epoch): single 6.1 / 5.3, 0, 194, 100%, none; rr3 4.6 / 4.3, 0, 185, 100%, 1; rr3-peers 4.7 / 4.6, 0, 213, 100%, 1; hive3 4.5 / 4.0, 0, 171, 100%, 1. Token multiple vs single: rr3 0.95x, rr3-peers 1.10x, hive3 0.88x. Verdict on "3 agents faster than 1": directionally yes (p50 about 25% lower, mean 13-25% lower for every 3-replica arm), but not established: the task finishes in about 5 s, so wall time is dominated by dispatch overhead, n=3 per arm, the 120 s chaos restart never fired, and the 3-replica arms did not differ from each other beyond noise. Tokens did not rise with replicas. No switch follows either way (Q12). The run used the fixed `examples/bench.yaml` (its `model: sonnet` was rejected by the live API with a 422 and is now `claude-sonnet-5-5`; the first attempt failed on that, the run itself was identical to the fixed file).

- 2026-10-24, init scripts (D2): `spec.init_scripts` run once per cluster as reconciler Job `agent-<slug>-init` (`reconciler/init.py`), recorded in `clusters.status.init` `{state skipped|running|succeeded|failed, scripts_hash, started_at, finished_at, exit_code, log_tail, reason, job}`. Why: status has one writer (the reconciler) and survives restarts, so "once" is a recorded fact; a marker file on the RWX PVC written by the first agent pod races under Parallel pod management. The first converge decides: no scripts writes `skipped`, and a later edit never runs them on that cluster (edits apply to the next cluster). State is written before the create and `job` after it (the checks crash-safety pattern); the Job has no TTL and is deleted after the outcome is recorded, so an offline reconciler cannot lose it. Pod-local installs by a script do not reach agent pods: only the shared workdir is shared (`.agent-init/init.sh`, `init.log`, `.gitignore` of `*`). A failed run starts sessions with phase `degraded` instead of blocking them, so a broken cluster can still repair itself. INIT_SH is passed in argv chunks of 16384 characters because Linux caps one argument at 128 KiB and the spec allows 20 x 16384 characters.
- 2026-10-24, hive docs: amends the 2026-10-23 spec-immutability entry (D4): `spec.replicas` and `spec.init_scripts` are the only spec fields that change in place, with no generation bump and no pod roll; every other field stays fixed and `PATCH /api/v1/clusters/{id}` stays 405. Why: scaling and init scripts must work on a running hive without rolling agents that hold sessions and locks. Owned contract part `orch-spec-runtime-mutable`, documented in README `## API` Versioning.
- 2026-10-24, agent-to-orchestrator path (D1): agents call `/agent/v1` on a second listening socket of `orch api` (the agent port, `ORCH_AGENT_PORT`, 8001) that serves only `/agent/v1/*`, behind `HMAC(master_key, "agent:<cluster_id>")` mounted from the cluster Secret, plus caller-IP binding to `agents.pod_ip`; the matching agents row is the caller's identity. Why: the api has no auth of its own, so the agent surface gets its own port and token, and agents need synchronous answers. Rejected: per-agent tokens (one Secret per StatefulSet), wrapper events and the ingester (async, no answers), a separate agent-api process (a second writer), the same port with an exempt prefix (rides the ingress). The main port answers 404 for `/agent/v1`.
- 2026-10-24, tool visibility is fixed at render from `max_replicas` and `static`, not from the live replica count. Why: the pod spec must not depend on how many agents run now, or a scale would roll pods to change their tools; a hive is by definition a cluster whose cap exceeds 1. The renderer in `k8s/on_start.py` also owns the plugin name `orchestrator`: its entry replaces a user entry of that name, and specs naming it are rejected.
- 2026-10-24, wrapper peer seeds are rendered from the cap (`range(max_replicas or replicas)`), not the current replicas. Why: agents added by scaling then find each other without any pod rolling; a seed whose pod does not exist yet is simply unreachable until it starts.
- 2026-10-24, amends the 2026-10-23 layering entry: `api/agent.py` may now import `agent_orchestrator.tokens`, alongside `api/workspace.py`; the pin in `tests/test_api_clusters.py::test_api_never_imports_k8s_or_wrapper` (`token_users`) was widened from workspace.py alone to workspace.py and agent.py. Why: the agent route must verify the same derived token the renderer put in the pod env. No other api module may import `tokens`, `wrapper`, k8s or reconciler; only workspace.py may import `wrapper`.
- 2026-10-24, the feed and `hive_state` pushes run in the dispatcher (`dispatcher/hive.py`), not the ingester. Why: the dispatcher already owns `cluster_leaders` and the claim lock, and the ingester must stay a pure event writer with one subscription per agent; the leader row, the feed cursor and the per-agent hashes then have a single writer.
- 2026-10-24, `LEADER_GRACE_SECONDS` (30, `db/leadership.py`) and `PUSH_INTERVAL_SECONDS` (10, `dispatcher/hive.py`) are module constants, not settings. Why: they are protocol timings that tests and the docs pin, and an operator tuning them per deployment would only create untested combinations.

- 2026-10-25, hive push loop (`dispatcher/hive.py`): `cluster_leaders.state_hash` is a JSON map `{agent_id: hash}` (text column, dispatcher the only writer) so one unreachable agent never re-pushes the others; the lock is held only around the DB read and the DB write, never across wrapper HTTP. The feed settle window judges `events.created_at` (DB insert time, `DEFAULT clock_timestamp()` added to migration 0003, filled by the DB so the ingester stays the only writer), not `events.ts`: ts is the wrapper's envelope time, so a replayed catch-up row with an old ts and a low id committing late would count as settled and be skipped for good. Chosen over a pg_snapshot xmin test because one long transaction anywhere in the database would stall the feed. The push claims its work (feed cursor and per-agent hashes) in the locked read phase and undoes only failed hive_state claims afterwards, so a second dispatcher never repeats a push. Pending Bash calls and the in-memory read watermark are lost on a dispatcher restart: the stored cursor is held below the oldest pending call, so a restart can repeat a few feed lines, never skip one.

- 2026-10-23, exception to the additive-only `/api/v1` rule: `PATCH /api/v1/clusters/{id}` is removed (405, pinned by `tests/test_api_clusters.py::test_patch_cluster_retired_405`) and `POST /api/v1/clusters` needs exactly one of `spec` and `preset_id`. Why: a live spec edit bumped `generation` and rolled every agent pod of a running cluster; clusters now snapshot their preset spec at create and never change. Changing a spec means discarding the cluster and scheduling again from a preset. `check_spec` keeps its `stored` parameter only for the preset PUT (a stored out-of-list model, effort or image stays accepted when unchanged). The exception is documented in README `## API` Versioning.
- 2026-10-23, amends D5: the api now calls wrapper pods with derived per-cluster tokens, only through `api/workspace.py`, for the file and terminal proxies (user decision N1). Why: the wrapper is the only process with the workdir mounted and a PTY, and Kubernetes `pods/exec` is excluded, so there is no other way to serve a file tree or a terminal. Events stay stored, not proxied. Layering is pinned by `tests/test_api_clusters.py::test_api_never_imports_k8s_or_wrapper`: no other api module may import `agent_orchestrator.wrapper` or `agent_orchestrator.tokens`, and none may import k8s or reconciler. The derived token is sent only as the Authorization header (`WrapperTarget.token` is `repr=False`), and terminal ids are checked against `^term_[0-9a-f]{12}$` before any upstream path is built.
- Single-writer reading of "no shared state" (D2): the tatara rule "services talk only through the queue or HTTP APIs, no shared state" conflicts with a Postgres-only queue, so it means one writer per table. Queue tables (messages, commands, checks) are the only multi-writer tables, changed only through `WHERE status = '<expected>'` UPDATEs. Table writers are in README.md `## Architecture`.
- One wrapper session per pod: a pod is exactly one claude-code-wrapper session, and a single pod is an orchestrator session of 1. Peer messaging, round-robin and context gauges are per pod, never per multi-session pod.
- Events are stored, not proxied (D5): the ingester keeps one SSE subscription per agent and stores every event (at-least-once delivery, exactly-once storage via UNIQUE(agent_id, wrapper_session_id, seq)). Browsers and API clients read the stored rows, so history survives wrapper restarts, resume works from a global event id, and the api never holds wrapper tokens.
- openapi.json is generated: after any route or schema change run `uv run python -m agents_orchestrator.api.openapi > openapi.json`; tests/test_readme_api.py fails on drift and on undocumented routes.
- 2026-10-24: chart `components.<name>.podAnnotations` merge over global `podAnnotations` (component wins). Why: the cluster's oauth2-proxy admission webhook (Go injector 0.4.7) rejects any annotated pod whose first container has no ports, and global podAnnotations reach the port-less dispatcher/ingester/reconciler too, so SSO annotations must target the api pod alone.
- 2026-10-24: react-resizable-panels `Separator` pitfall: the library writes an INLINE `flex-basis: auto` (plus `flex-grow: 0; flex-shrink: 0`) on the separator element, which beats a styled `flex: 0 0 4px` shorthand, so a childless separator renders 0px wide and its colour never shows (dragging still works through pointer hit regions). Size it with an inline `style={{ flexBasis: ... }}` (props.style is spread after the defaults), never with a stylesheet `flex` rule. Why recorded: the dividers were invisible in the live UI while every jsdom test passed.
- 2026-10-24, amends D25 (prior web-ui epic: "event-driven refresh plus a manual refresh button; no inotify", user decisions U2, X2): the "Refresh files" button is removed. `FilesPanel` now polls `pollExpanded()` every 3 s while `document.visibilityState` is visible, plus one pass on `visibilitychange` to visible and on every event stream open, and refetches the open preview when its entry mtime or size changes in the parent listing. The stream path (`fileEvents`) stays for instant agent writes. Why: terminal shells, check jobs and any writer outside the agent hooks produce no events, and a tree that loaded in error (409) or missing only recovered by clicking. Still no inotify and no backend or API change: the tree reads the existing files API. No timer runs while the tab is hidden or the panel is unmounted.
- 2026-10-24 (cluster-scaling): `spec.replicas` is scale-writable in place, by the api only, through `db.clusters.set_replicas` (single writer; `jsonb_set` under a `clusters` row lock, NOTIFY `cluster_changed`). No `generation` bump: the hash invariant keeps a replica count off the pod template, so a replica change never rolls pods. Refusal codes, checked in this order: `cluster_deleting`, `not_leader` (a caller agent that is not the `cluster_leaders` agent), `static_cluster`, `out_of_range` (outside 1..`max_replicas`), `leader_would_leave` (the leader's ordinal >= the new count; Q4 is handover only, a scale-down never removes the leader). An unchanged value writes and notifies nothing. `cluster_leaders` and `agents` are only read here (dispatcher and reconciler stay their writers).
- 2026-10-25 (configuration-improvements): `render._apply_wrapper` renders `spec.wrapper` into the wrapper config with every user string (values, lists and nested values, never keys) passing through `_escape`, which doubles `$` to `$$`; reserved entries (on-start hook, lock-check hook, the three built-in denies, `any-mcp`, the ask-in-writing prompt) are rendered first and user entries are appended after them. Why: the wrapper interpolates `${VAR}` from the pod env into the whole config, so an unescaped user value such as `${CLAUDE_CODE_OAUTH_TOKEN}` in a webhook url or prompt would leak the OAuth token (user decision); `$$` yields the literal text there while a command hook's shell still expands `$VAR` at run time. Reserved-first keeps a user from removing or reordering the safeguards the orchestrator depends on. Rendered orchestrator values (`${CCW_AUTH_TOKEN}`, the lock-check headers) are not escaped.

- 2026-10-25 (configuration-improvements): `leader_lease_seconds` amends hive D26 ("no forced handover") for clusters that set it: step 4 of `leadership_pass` hands leadership to the ready agent free the longest (reason `lease_expired`) once the leader's term outlives the lease, only when the leader is idle with no `dispatching` or `verifying` message. D21 (no takeovers) is kept: it is a handover of the current leader's own term, applied by the dispatcher at the turn boundary, never mid-turn, and an agent cannot trigger it. Why: a hive leader otherwise leads indefinitely, so one agent's context and load never rotate; the user approved a time-based rotation that cannot interrupt work. Clusters without the field are unchanged. `LEADER_GRACE_SECONDS` stays a constant 30.

- 2026-10-25 (configuration-improvements): autoclose is an api background sweeper (`api/autoclose.py`, poll 10 s) that calls `db.clusters.close_expired`, one status-guarded UPDATE that makes the same write as `request_delete` and NOTIFYs `cluster_changed`. Chosen over a derived predicate (the reconciler treating an expired active cluster as deleting) and over a reconciler write of `desired`. Why: a derived predicate leaves `desired` saying `active` while the cluster is being discarded, so the api, the web page and message acceptance would disagree with the reconciler; a reconciler write breaks the single-writer rule (the api is the only writer of `clusters.desired`). The guard `WHERE desired = 'active'` makes several api replicas safe. Counts from `created_at` (user decision), uses the existing discard path, minimum `ORCH_AUTOCLOSE_MIN_SECONDS` 300.

- 2026-10-25 (agents-webhook-microservice): in-cluster services authenticate to the orchestrator with service tokens on a dedicated port (`ORCH_SERVICE_PORT`, bearer token, only the sha256 configured in `ORCH_SERVICE_TOKENS`), a fixed route list, never `/agent/v1` or a WebSocket. Chosen instead of Keycloak client credentials: the oauth2-proxy injector's JWT audience is unknown, so a verifier could not be pinned. The source-allowlist trust model stays unchanged: service pod CIDRs are not added to `ORCH_ALLOWED_CIDRS`, the port skips the allowlist and the token is the credential. Documented in README Security, Service tokens.

- 2026-10-26 (workspace-s3-cache) D1: the cache restore and save run as separate Jobs (`agent-<slug>-cache-restore|save`) in `ORCH_CACHE_IMAGE`, not in the agent pod. Why: the agent pod runs user-controlled code and a prompt-driven agent; a Job with only the workspace PVC mounted, a hardened pod and no Secret keeps the transfer out of the agent's reach, and the save runs after the pods are gone so the workdir is quiet.
- 2026-10-26 (workspace-s3-cache) D2: the Jobs get one presigned URL in `CACHE_URL`, signed by the reconciler, which alone holds the S3 credentials. Why: a leaked Job env or log exposes a single object URL that expires (`ORCH_CACHE_TIMEOUT_SECONDS` + 600 s), never the access key; the URL query is redacted from every reason and log line.
- 2026-10-26 (workspace-s3-cache) D4: sessions sharing a cache key share one archive and last writer wins; no locking or merge. Why: a lock would need shared state beyond the single-writer database and a stuck holder would block discards; a cache is allowed to be replaced, and the object store write is atomic per object.
- 2026-10-26 (workspace-s3-cache) D11: the save skips (no Job, state `skipped`) when the restore is still running or failed with `download_failed`, `timeout`, `job_missing`, `foreign_object`, `job_create_failed` or `not_configured`; an `extract_failed` restore still saves. Why: after a restore that could not fill the workdir, a save would overwrite a good archive with an empty or partial tree; a corrupt archive is the one case where replacing it is the point. Symlinks pointing outside the workdir are skipped on save and counted in `skipped_links`, and a save over `ORCH_CACHE_MAX_BYTES` fails `too_large` with no upload, keeping the previous archive.
